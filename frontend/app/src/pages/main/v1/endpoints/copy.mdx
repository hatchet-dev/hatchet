# Diagnosis: why a request failed

## request.healthcheck
The healthcheck

## request.delivery
Task delivery

## failure.step.logs
Check the endpoint's server logs for the failing request.

## failure.step.logsCommand
Check the endpoint's logs (`[[command]]`) for the failing request.

## failure.operatorToken.title
The operator cannot authenticate for this tenant

## failure.operatorToken.detail.cloud
Hatchet cannot authenticate this tenant. We are looking into it.

## failure.operatorToken.detail.oss
The serverless operator has no API token for this tenant, so it cannot register the workflows the endpoint serves.

## failure.operatorToken.steps.oss
- This is a Hatchet-side problem, not an endpoint problem: check the serverless operator logs on the Hatchet instance.
- For an out-of-process operator, make sure it is configured with credentials for this tenant.

## failure.secretUnusable.title
The signing secret cannot be used

## failure.secretUnusable.detail
Hatchet could not load this endpoint's signing secret.

## failure.secretUnusable.steps
- Rotate the signing secret from Edit, and set the same value as `HATCHET_SIGNING_SECRET` on the endpoint.

## failure.blocked.title
The URL is blocked by the delivery policy

## failure.blocked.detail
Hatchet only calls endpoints over https on port 443 at public addresses. Loopback and private network addresses are refused.

## failure.blocked.steps
- Use the public https URL of the deployment.
- For local development, put a public https tunnel (for example cloudflared) in front of the endpoint.

## failure.blocked.step.oss
To call endpoints on your own machine or private network during local development, set `SERVER_SERVERLESS_OPERATOR_INSECURE_DESTINATIONS=true` on the engine. This turns off the delivery policy entirely, so never set it in production.

## failure.dns.title
The endpoint's hostname does not resolve

## failure.dns.detail
[[what]] failed because DNS has no record for the host.

## failure.dns.steps
- Check the URL for typos.
- Make sure the deployment exists and is published at that hostname.

## failure.tls.title
TLS handshake failed

## failure.tls.detail
[[what]] could not establish a trusted https connection.

## failure.tls.steps
- Make sure the hostname serves a valid, publicly trusted certificate.
- Custom domains can take a few minutes to get a certificate after they are added.

## failure.timeout.title
[[what]] timed out

## failure.timeout.healthcheck.detail
The endpoint did not answer the healthcheck in time. Healthchecks should be fast: they only list the workflows the endpoint serves.

## failure.timeout.healthcheck.step
Avoid slow work (network calls, large imports) when the handler starts; cold starts count against the timeout.

## failure.timeout.delivery.detail
The endpoint did not answer within the request timeout.

## failure.timeout.delivery.step
Raise the endpoint's request timeout if the task legitimately runs longer, keeping it within the platform's maximum duration.

## failure.connection.title
The endpoint closed the connection

## failure.connection.detail
[[what]] reached the host but the connection was refused or dropped.

## failure.connection.step
Make sure the deployment is running and serves https on port 443.

## failure.auth.title
The endpoint rejected the request signature

## failure.auth.detail
[[what]] was refused with status [[status]]. This almost always means the signing secrets differ, or something in front of the endpoint requires its own authentication.

## failure.auth.steps
- Make sure `HATCHET_SIGNING_SECRET` on the endpoint is exactly the signing secret registered here. If unsure, rotate the secret from Edit and set the new value on the endpoint, then redeploy.
- Make sure the endpoint's clock is correct: signed requests older than 5 minutes are refused.

## failure.auth.step.CLOUDFLARE_WORKERS
Cloudflare Access or WAF rules in front of the Worker block the operator. Exempt the Hatchet routes from them.

## failure.auth.step.VERCEL
Vercel Deployment Protection answers 401/403 before your code runs. Use the production domain, or turn protection off for the deployment.

## failure.auth.step.GENERIC_HTTP
Authentication or firewall rules in front of the endpoint must let the Hatchet routes through.

## failure.notFound.title
Nothing is served at this URL

## failure.notFound.detail
[[what]] got status [[status]]: the host answered, but not with a Hatchet handler at this path.

## failure.notFound.step.healthcheckPath
The [[platform]] adapter serves the healthcheck at `[[path]]`; check the URL ends with that path.

## failure.notFound.step.triggerPath
The [[platform]] adapter serves tasks at `[[path]]`; check the URL ends with that path.

## failure.notFound.step.path
Check the path in the URL matches the route your handler is mounted on.

## failure.notFound.step.redeploy
Make sure the latest deployment includes the Hatchet handler.

## failure.redirect.title
The endpoint redirected

## failure.redirect.detail
Hatchet does not follow redirects, so the URL must point at the final location.

## failure.redirect.steps
- Open the URL in a browser to see where it redirects (often a trailing slash, www., or a custom domain) and register that URL instead.

## failure.rateLimited.title
The endpoint is rate limiting Hatchet

## failure.rateLimited.detail
[[what]] was refused with status 429.

## failure.rateLimited.steps
- Raise the platform's rate limits for the Hatchet routes, or increase the poll interval.

## failure.serverError.title
The endpoint is erroring

## failure.serverError.detail
[[what]] got status [[status]]: the endpoint's code threw or the platform could not run it.

## failure.serverError.step
Make sure required environment variables (`HATCHET_SIGNING_SECRET`, `HATCHET_CLIENT_TOKEN`) are set on the deployment.

## failure.clientError.title
The endpoint refused the request (status [[status]])

## failure.clientError.detail
[[what]] got status [[status]].

## failure.notHealthcheck.title
The response is not a Hatchet healthcheck

## failure.notHealthcheck.detail
The URL answered successfully, but the body is not the JSON a Hatchet serverless handler returns. The URL probably points at a page of your app instead of the Hatchet route.

## failure.notHealthcheck.step.path
Point the healthcheck URL at `[[path]]` on the deployment.

## failure.notHealthcheck.step.noPath
Point the healthcheck URL at the route your Hatchet handler serves.

## failure.notHealthcheck.step.handler
Make sure the handler is built with the Hatchet serverless SDK, or implements the healthcheck contract.

## failure.catalog.title

## failure.catalog.detail

## failure.catalog.steps

- The same workflow definitions should register on a regular worker; try that to see the full validation error.
