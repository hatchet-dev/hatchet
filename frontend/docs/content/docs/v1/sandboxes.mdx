# Sandboxes

<Callout type="info">Sandboxes are available on Hatchet Cloud only.</Callout>

<Callout type="warning">
  Sandboxes are a Labs feature and may change in future releases. Turn them on
  under <strong>Labs Preview</strong> in your tenant settings.
</Callout>

A sandbox is a workspace with a shell on a machine. You may run commands in it as well as carry out filesystem operations such as reading and writing files. Agents that write and run code, untrusted plugins, and jobs that need an isolated environment perfectly fit in this use case.

Hatchet does not run the machines itself. You connect a sandbox vendor to your tenant with your own account. Hatchet drives it and keeps the snapshot lineage in the form of Hatchet tasks.

## How it works

- A **provider** is a vendor account connected to your tenant: Daytona, E2B, Archil or Freestyle. You add it once in the dashboard with the vendor's API key.
- A **sandbox operator** runs inside Hatchet Cloud. For each tenant with sandboxes turned on it registers a `hatchet-sandbox` task and serves every call by talking to the vendor.
- A **snapshot** is the saved state of a sandbox's workspace. A sandbox can be started again from its latest snapshot. You may also fork an existing snapshot for a newly created sandbox.

## Connect a provider

<Steps>

### Turn sandboxes on

Open your tenant settings, pick **Labs Preview** and turn on **Sandboxes**. You need to be a tenant owner or admin. A **Sandboxes** entry appears in the sidebar.

### Add a provider

Under **Sandboxes**, choose **New provider** and pick a vendor. Give it a name, which is what your code passes as `provider`, and paste the vendor's API key.

The optional fields:

| Field                   | What it does                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Default template        | The image, template or snapshot new sandboxes start from when `create` does not name one.                                                              |
| Max idle time (seconds) | How long a sandbox with no calls stays running before the vendor stops it. Default 3600. A call to `connect` starts a stopped or paused sandbox again. |
| Provider config         | JSON for vendor-specific settings                                                                                                                      |
| Labels                  | Free-form tags for your own bookkeeping. These are passed to the sandbox vendor to link against each sandbox started                                   |

### Wait for the connection to be healthy

The provider page shows the credential check and an event log. A provider whose key stops working is marked unhealthy, with the vendor's error, and new calls on it fail with that message.

</Steps>

### Vendors

| Vendor                            | Template means                  | Provider config keys                                 | Notes                                                                                                                                                                                                                |
| --------------------------------- | ------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Daytona](https://www.daytona.io) | A Daytona snapshot name         | `apiUrl`, `template`, `workdir`                      | Snapshots are Daytona snapshots. The default workspace is `/home/daytona`.                                                                                                                                           |
| [E2B](https://e2b.dev)            | A template name or snapshot ID  | `apiUrl`, `template`, `workdir`, `maxTimeoutSeconds` | Snapshots are filesystem-only templates. E2B caps a session at one hour on most plans; `maxTimeoutSeconds` raises the cap on plans that allow it. The default workspace is `/home/user`.                             |
| [Archil](https://archil.com)      | An OCI image, such as `node:24` | `region`, `apiUrl`, `template`, `workdir`            | Keys are scoped to one region; set `region` to `aws-us-east-1` (default), `aws-us-west-2`, `aws-eu-west-1` or `gcp-us-central1`. A snapshot is a stopped fork of the machine. The default workspace is `/workspace`. |
| [Freestyle](https://freestyle.sh) | A snapshot ID or slug           | `apiUrl`, `template`, `workdir`                      | Snapshots include memory, so a resumed sandbox continues where it stopped. The default workspace is `/workspace`.                                                                                                    |

`snapshotEveryTurn: true` in the provider config takes a snapshot after every call that changes files, so each `exec` and `files.write` result carries a `snapshotId` you can fork from. Without it, a snapshot is taken when you `kill` the sandbox, which is enough to `connect` to it later. Snapshots cost time and vendor storage, so turn this on only when you fork often.

## Using sandboxes

The SDK is `@hatchet-dev/sandbox` for TypeScript. Import it once and it adds `hatchet.sandbox` to your Hatchet client.

```bash
pnpm add @hatchet-dev/sandbox @hatchet-dev/typescript-sdk
```

```typescript
import { HatchetClient } from "@hatchet-dev/typescript-sdk/v1";
import "@hatchet-dev/sandbox";

const hatchet = HatchetClient.init();

export const session = hatchet.durableTask({
  name: "agent-session",
  executionTimeout: "1h",
  fn: async (input: { conversationId: string }) => {
    const sandbox = await hatchet.sandbox.create({
      id: input.conversationId,
      provider: "e2b",
      metadata: { conversation: input.conversationId },
    });

    await sandbox.files.write("main.py", 'print("hello from the sandbox")');
    const result = await sandbox.exec("python3 main.py");

    await sandbox.kill();
    return { stdout: result.stdout, exitCode: result.exitCode };
  },
});
```

`provider` is required when the tenant has more than one provider. With a single provider it can be left out.

### Commands and files

- `exec(cmd, { timeoutMs })` runs `sh -c cmd` in the workspace and returns `stdout`, `stderr` and `exitCode` together when the command ends. A non-zero exit is a normal result, not an error. A command that hits its timeout returns exit code `124`.
- `files.read`, `files.write`, `files.list`, `files.exists`, `files.getInfo`, `files.makeDir`, `files.rename`, `files.copy` and `files.remove` work on paths relative to the workspace. A path outside the workspace throws a `FilesystemError` with code `invalid_path`.
- `files.download(url, path)` and `files.upload(path, url)` move files between the workspace and an https URL. The operator does the transfer, so the sandbox needs no network for it. Private and loopback addresses are refused.
- Up to 2 MiB passes through Hatchet per `read` or `write`. Larger files are staged with the provider and never pass through Hatchet; you call the same methods either way.

### Coming back to a sandbox

Every sandbox has an ID. Pass your own with `create({ id })` or take `sandbox.sandboxId`. From anywhere with a Hatchet client:

```typescript
const sandbox = await hatchet.sandbox.connect("conv-42");
await sandbox.exec("git status");
```

If the sandbox was stopped, because it was idle or you called `kill`, `connect` starts it again from its latest snapshot.

### Forks

Start a new sandbox from any snapshot with `create({ from })`. Create two from the same snapshot and you have a fork, which is how you try two approaches from the same starting point.

```typescript
const base = await hatchet.sandbox.create({ provider: "e2b" });
await base.exec("git clone https://github.com/you/repo . && npm ci");
await base.kill();

const [a, b] = await Promise.all([
  hatchet.sandbox.create({ from: base.sandboxId, inheritParentMetadata: true }),
  hatchet.sandbox.create({ from: base.sandboxId, inheritParentMetadata: true }),
]);
```

A fork always runs on the provider that holds its snapshot.

### Finding and cleaning up

`hatchet.sandbox.list({ metadata })` returns the sandboxes whose tags include every pair you pass. `hatchet.sandbox.delete({ metadata })` deletes every match with all of its snapshots, and returns their IDs. Both filters are subset matches, so `{ conversation: "42" }` matches a sandbox tagged `{ conversation: "42", user: "ada" }`.

`kill()` stops the machine and keeps the snapshots, so `connect` still works and you stop paying the vendor for a running machine. `delete()` removes the sandbox, its snapshots and its staged files from the vendor.

<Callout type="info">
  Idle sandboxes stop on their own after the provider's max idle time, 3600
  seconds by default. Stopped sandboxes still hold their snapshots at the vendor
  until you delete them.
</Callout>

## Inside durable tasks

Each sandbox call inside a durable task is a durable child. When the task is replayed after a crash, calls that already finished return their recorded result without touching the vendor, so a command never runs twice. Two things follow from that:

- Keep every sandbox call inside the durable task, not in a helper that runs outside it.
- Turning sandboxes on for a tenant that already has in-flight durable tasks using an older sandbox provider makes those tasks fail on resume, because the task name changed under them. Drain them first.

## What to know

- **One call at a time per sandbox.** Calls on the same sandbox run one after another. Calls on different sandboxes run in parallel.
- **Output arrives when the command ends.** There is no streaming of a running command's output. Long commands should write to a file you read afterwards.
- **Processes outside a call keep running.** A command that starts a background process leaves it running, and later calls can see it. Anything that ran in the sandbox earlier can read what runs in it later.
- **Only the workspace is snapshotted** on filesystem-only vendors. Files elsewhere survive while the machine is running and are gone after a resume from snapshot. Never write credentials to the workspace: they end up in every snapshot and fork.
- **Vendor limits apply.** Session length, machine size and storage are the vendor's, and plan limits surface as the task's error message.

## Where to look

- Every call is a run of the `hatchet-sandbox` task in the **Runs** page, tagged with `hatchet.sandbox.fn`, `hatchet.sandbox.id`, `hatchet.sandbox.image` and `hatchet.sandbox.from` so you can filter by sandbox or by operation.
- The provider page under **Sandboxes** lists the provider's events: machines created, failed turns, failed snapshots and health changes.
- With OpenTelemetry set up, sandbox calls appear as spans in the calling task's trace. Set `HATCHET_SANDBOX_OTEL=false` to turn that off.
