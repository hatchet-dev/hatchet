# API Tokens

API tokens authenticate workers and applications with a single Hatchet tenant. Each token holds a set of capabilities, and every REST operation and gRPC call it makes must be granted by one of them. Give each token only the capabilities its worker or application needs.

## Create a token

Sign in as a tenant **ADMIN** or **OWNER**, then open **Settings > API Tokens** and select **Create API Token**. Enter a name, choose an expiration, and choose its access:

- **Total read access** selects every capability a tenant **VIEWER** can read: runs, schedules, workflows, events, filters, webhooks, serverless endpoints, workers, rate limits, streams, metrics, and tenant settings.
- **Total write access** selects everything else, including running a worker, triggering, cancelling, and replaying runs, pushing events, and managing members.

Both are selected by default. Deselect either, or any individual capability below them, to narrow the token. Select **Create token** to review every capability the token will hold, then **Accept and create**. Copy the generated token and store it securely. It is only displayed once. The tokens table's **Access** column shows **Read and write**, **Read**, or the token's capabilities.

When creating a token through the REST API with an admin or owner session, pass the capabilities in the create request, for example `"capabilities": ["worker"]`. Omitting `capabilities` creates a token holding `all`, with both read and write access. The `hatchet-admin token create` command takes the same list through `--capabilities`. Token list responses include each token's `capabilities`. API tokens cannot authenticate token-creation requests.

## Capabilities

Capabilities are grouped by resource, and most come in pairs such as `runs:read` and `runs:trigger`. Two cover a whole process:

- `worker` grants everything a worker needs: registering workflows, receiving and completing tasks, triggering child runs, reading their results, publishing to streams, and exporting traces.
- `operator` grants what a serverless operator needs.

On Hatchet Cloud, `infra:read` and `infra:write` cover managed compute, sandbox providers, and autoscaling. They are not listed on self-hosted instances, where those features do not exist.

`read-only` is the **Total read access** selection as a single capability. A token holding it keeps any reads added to Hatchet later.

No token can list, create, or revoke API tokens, change Labs entitlements, or call user-account operations, such as creating a tenant or accepting an invite, whatever its capabilities.

**Payloads remain visible** to any token that can read a resource, including task inputs and outputs, event payloads, and log payloads. The member-level **Can view payloads** setting does not apply to API tokens.

## Worker configuration

Workers need the `worker` capability, which both the default selection and **Total write access** include. Configure the token through `HATCHET_CLIENT_TOKEN` or the SDK's token option:

```bash
export HATCHET_CLIENT_TOKEN="<your-worker-token>"
```

A gRPC call the token's capabilities do not grant returns `PermissionDenied` with the procedure it tried to call. See [Troubleshooting Workers](/v1/troubleshooting#permissiondenied-from-an-api-token) if a worker cannot connect.

## Older tokens

Tokens created before capabilities existed keep the access they were created with. Unrestricted tokens show **Read and write**. Read-only tokens show **Read (REST only)**: they hold the **Total read access** capabilities over the REST API, and every gRPC call they make returns `PermissionDenied`.

The REST API still accepts `readOnly: true` and creates the same kind of read-only token, so existing scripts and SDK calls keep working. It cannot be combined with `capabilities`; to give a token read access that also works over gRPC, pass `"capabilities": ["read-only"]` instead.

## Change access or revoke a token

A token's capabilities cannot be edited. To change them, revoke the token and create a replacement. Update any applications using the token.

Only an admin or owner session can list, create, or revoke API tokens.
