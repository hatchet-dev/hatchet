# Profiles

The Hatchet CLI supports managing multiple Hatchet instances and tenants using named profiles. This feature makes it easy to switch between different environments, such as development, staging, and production.

## Creating a Profile

You can create a new profile using the `hatchet profile add` command. You will need to provide a Hatchet API token for the profile.

```sh
hatchet profile add
```

This command will prompt you to enter the API token followed by the profile name. You can also provide these as flags:

```sh
hatchet profile add --name [name] --token [token]
```

## Listing Profiles

You can list all the profiles you have configured using the `hatchet profile list` command:

```sh
hatchet profile list
```

This will display all configured profiles, with the default profile marked with `(default)` if one is set.

## Setting a Default Profile

You can set a profile as the default using the `hatchet profile set-default` command. The default profile will be automatically used when no profile is specified with the `--profile` flag.

When no default is configured, `hatchet server start` sets the profile it creates as the default. Commands that take the `--profile` flag also use the only configured profile without prompting.

```sh
# Set default profile interactively (prompts for selection)
hatchet profile set-default

# Set a specific profile as default
hatchet profile set-default --name [name]
```

Once a default profile is set, you can run commands without specifying the `--profile` flag:

```sh
# Uses the default profile
hatchet worker dev
```

To unset the default profile:

```sh
hatchet profile unset-default
```

## Using a Profile

To use a specific profile for your Hatchet CLI commands, you can specify the profile name using the `--profile` flag. This overrides the default profile if one is set.

```sh
hatchet worker dev --profile [name]
```

<Callout type="info">
  In a session without a terminal, such as CI, commands cannot prompt for a
  profile and fail with an error if they try. Pass `--profile` or set a default
  profile first.
</Callout>

## Updating a Profile

You can update an existing profile using the `hatchet profile update` command. This allows you to change the API token associated with a profile.

```sh
hatchet profile update
```

## Deleting a Profile

You can delete a profile using the `hatchet profile remove` command:

```sh
hatchet profile remove
```

If you remove a profile that is set as the default, the default profile setting will be automatically cleared.

## Where Tokens Are Stored

Profile metadata lives in `~/.hatchet/profiles.yaml`. API tokens are stored in the system secret store instead of that file: the macOS Keychain, or the Secrets Service on Linux (GNOME Keyring, KWallet). `profiles.yaml` then contains no credentials, so it is safe to inspect, back up, or sync.

When no secret store is available, for example on a headless Linux server, in a container, or in CI, the CLI falls back to writing tokens into `profiles.yaml` and prints a warning. Set `tokenStore` in `~/.hatchet/config.yaml` (or the `HATCHET_CLI_TOKEN_STORE` environment variable) to control this explicitly:

| Value     | Behavior                                                    |
| --------- | ----------------------------------------------------------- |
| `auto`    | Use the system secret store when available, otherwise file. |
| `keyring` | Always use the system secret store; fail if unavailable.    |
| `file`    | Always keep tokens in `profiles.yaml`; no warnings.         |

### Migrating Existing Profiles

Profiles created by older CLI versions keep their tokens in `profiles.yaml`. The first time you run a command in a terminal, the CLI offers to move them. Declining sets `tokenStore: file` so you are not asked again. You can also migrate at any time:

```sh
# Move all plain-text tokens into the system secret store
hatchet profile migrate-tokens

# Move tokens back into profiles.yaml, e.g. before copying it to a machine without a keyring
hatchet profile migrate-tokens --to file
```

`hatchet profile list` and `hatchet profile show` mark any profile whose token is still stored in plain text.

<Callout type="warning">
  Moving tokens with <code>--to file</code> writes them in plain text. Anyone
  who can read <code>profiles.yaml</code>, including backups and dotfile syncs,
  can act as you on your tenants until the tokens expire or are revoked. The
  command asks for confirmation in a terminal and requires <code>--yes</code>{" "}
  when run from a script.
</Callout>

<Callout type="info">
  A migrated `profiles.yaml` has no tokens in it, so CLI versions that predate
  this feature cannot read those profiles. Run{" "}
  <code>hatchet profile migrate-tokens --to file</code> before downgrading.
</Callout>
